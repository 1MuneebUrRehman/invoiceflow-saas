# InvoiceFlow — Technical Project Overview (Interview Edition)

> Use this document to explain the project to a technical interviewer. It covers what the
> product does, how it is built, every feature, the key architectural decisions, and the
> trade-offs behind them — i.e. the things interviewers actually ask about.

---

## 1. Elevator Pitch (30 seconds)

**InvoiceFlow is a multi-tenant invoicing SaaS for freelancers and small agencies.**
Each team gets an isolated workspace where they manage clients, build invoices with line
items and taxes, send branded PDF invoices by email, and get paid online through Stripe
Checkout via a secure public link. Overdue invoices are chased automatically with
scheduled reminder emails. It also ships a token-authenticated REST API (v1) and a
Free/Pro plan system with limits enforced in middleware and billing managed through the
Stripe Customer Portal.

## 2. Tech Stack

| Layer | Technology | Why |
|---|---|---|
| Backend | PHP 8.5, Laravel 13 | Current releases, greenfield project with no legacy constraints |
| UI | Livewire 4 + Tailwind CSS 4 | Reactive UI without a separate JS frontend; state stays server-side |
| Database | MySQL 8 | Production engine used in dev **and** tests (strict mode, real constraint semantics) |
| Payments | Stripe Checkout + Customer Portal (`stripe/stripe-php`) | PCI burden stays with Stripe; portal handles plan upgrades/cancellations |
| Auth | Session (web) + Laravel Sanctum tokens (API) | Standard Laravel auth for the app; bearer tokens for the API |
| Background work | Laravel Queues + Scheduler | PDFs, emails, and reminders never block requests |
| Testing | Pest 4 (feature-test heavy) | Tests run against real MySQL, including cross-tenant isolation assertions |
| Code quality | Laravel Pint + Larastan (PHPStan) | Formatting and static analysis enforced |

## 3. Complete Feature List

### 3.1 Multi-tenant workspaces
- Registration creates a **Tenant** (workspace) plus its **owner User** in one action
  (`app/Actions/Auth/RegisterTenant.php`).
- Roles: `Owner` / `Member` (`UserRole` enum).
- Every domain model (Client, Invoice, InvoiceItem, Payment) uses a `BelongsToTenant`
  trait → global query scope + auto-stamping of `tenant_id` on create.
- The active tenant lives in a container-scoped `CurrentTenant` object, set by
  middleware: `SetCurrentTenant` (web session) and `SetCurrentTenantForApi` (Sanctum).
- Isolation is proven by dedicated Pest tests that assert cross-tenant access fails.

### 3.2 Client management (CRM-lite)
- CRUD for clients: name, company, email, phone, full address, preferred currency, notes.
- Searchable client list (name / email / company) in both UI and API.

### 3.3 Invoice builder
- Line items (description, quantity, unit price), invoice-level tax rate, discounts.
- **Per-tenant sequential numbering** like `INV-2026-0001`, generated by a dedicated
  `GenerateInvoiceNumber` service inside a DB transaction (no duplicate numbers under
  concurrency; unique `(tenant_id, number)` constraint backs it up).
- Status lifecycle as a backed PHP enum: `Draft → Sent → Paid / Overdue / Cancelled`,
  with `isPayable()` logic and consistent badge colors mapped on the enum itself.
- Totals (`subtotal`, `tax_amount`, `total`) are **stored, not computed on read** — an
  invoice is a financial snapshot that must not drift if tax/rounding logic changes later.
- Confirmation modal before destructive/irreversible actions (e.g. sending).

### 3.4 Branded PDF invoices
- PDF generated in the background by a queued job (`GenerateInvoicePdf`).
- Tenant can upload a business logo (Settings → Business logo) which appears on the PDF
  and emails; stored via Laravel filesystem (`storage:link`).

### 3.5 Sending & online payments
- "Send Invoice" action (`SendInvoice`) queues an email (`InvoiceMail`) with the PDF and
  a **signed public link**.
- Public invoice page (`/invoice/{publicId}`) is a Livewire page protected by Laravel's
  `signed` middleware — the URL is tamper-proof and unguessable.
- Public identifiers are **ULIDs** (`public_id`), never auto-increment IDs — sequential
  IDs in URLs leak business volume and invite enumeration.
- The client clicks "Pay" → `CreateStripeCheckoutSession` action → Stripe Checkout.
- Success/cancel callbacks regenerate the signed URL **server-side**, so the
  client-facing callback URL never carries a signature.

### 3.6 Stripe webhook handling
- `POST /webhooks/stripe` (CSRF-exempt, signature-verified).
- On successful payment, `MarkInvoicePaid` records a `Payment` (provider enum:
  `Stripe` / `Manual`), updates `amount_paid`, and flips status to `Paid`.
- Fires an `InvoicePaid` **event**; queued listeners send receipts/update metrics —
  keeps the webhook handler fast and safe for Stripe retries (idempotent).

### 3.7 Automated overdue handling & reminders
- Two scheduled console commands (`routes/console.php`):
  - `MarkOverdueInvoices` — daily at 00:05, flips past-due `Sent` invoices to `Overdue`.
  - `SendInvoiceReminders` — daily at 09:00, emails reminders at **+3, +7, and +14 days**
    past due.
- Reminders are **idempotent**: a `reminders_sent` column tracks which tiers were sent so
  re-runs never double-email a client. All emails go through the queue.

### 3.8 Dashboard analytics
- Livewire computed properties: client count, **outstanding balance**, **overdue count**,
  **revenue this month**, recent invoices, and a revenue chart.
- Aggregates are cheap `SUM()` queries because totals are persisted (see 3.3).

### 3.9 REST API v1 (Sanctum)
- Token issuance: `POST /v1/auth/tokens` (email + password + device name), rate-limited
  (10/min/IP) against brute force; revoke with `DELETE /v1/auth/tokens/current`.
- Resources: full CRUD for **clients**, **invoices** (bound by `public_id` ULID),
  **payments** (list + record manual payment), invoice **send** endpoint, and **billing**
  endpoints (show plan, open Stripe portal).
- Eloquent **API Resources** shape all responses; pagination + `?search=` filtering.
- Invoice creation is **plan-gated by middleware** (`EnsureInvoiceLimit`).
- Documented in `docs/api.md`.

### 3.10 Plans & billing
- `TenantPlan` enum: **Free (3 invoices/month)** vs **Pro (unlimited)** — the limit lives
  on the enum (`monthlyInvoiceLimit()`), enforcement lives in `EnsureInvoiceLimit`
  middleware (web + API share it).
- Upgrades/downgrades/cancellation handled by the **Stripe Customer Portal** — no custom
  billing UI to maintain.

### 3.11 Auth & account features
- Register, login, logout, **forgot/reset password**, **email verification** (signed
  verification links, throttled resend).
- Settings page: business details + currency, logo upload/remove, profile, change
  password, **API token management** (create, list, revoke; plain-text token shown once).

## 4. Architecture Decisions & Trade-offs (the interview gold)

These are logged in `docs/decisions.md` — being able to defend them is the strongest
signal you can give an interviewer.

1. **Single-database multi-tenancy** (vs database-per-tenant à la stancl/tenancy).
   One schema to migrate, trivial backups, cheap hosting, easy aggregate reporting.
   *Trade-off:* isolation is application-layer — a missed scope is a data leak — so
   cross-tenant access is asserted throughout the API test suite. `tenant_id` on every
   table keeps a per-tenant export/migration path open.

2. **Tenant scope is a no-op without tenant context.** Console commands, queue workers,
   and seeders run unscoped on purpose — the overdue scanner must iterate *all* tenants.
   The alternative (silently empty queries) is the classic "the cron processed zero rows
   and nobody noticed" failure. The behavior is pinned by an explicit test.

3. **`User` is *not* tenant-scoped by the trait.** Global scopes on the auth model break
   session resolution and password resets. `users.tenant_id` is nullable to leave room
   for platform-admin users.

4. **Money as integer minor units (cents) + explicit `currency` column. No floats, ever.**
   Floats can't represent decimal currency; integer math is exact and rounding decisions
   are visible in code review. Tax *rate* is a decimal because it's a ratio, not money.

5. **Stored invoice totals** — financial documents are immutable snapshots; also makes
   dashboard aggregates cheap.

6. **Invoice-level tax rate, not per-line.** Target users bill at one rate; per-line tax
   complicates form, math, and PDF. The later migration path is mechanical.

7. **No repository pattern.** Eloquent *is* the persistence abstraction. Business logic
   lives in single-purpose **Action classes** (`app/Actions/`) that each own a DB
   transaction boundary. Controllers validate (Form Requests), authorize (Policies), and
   delegate — thin by design.

8. **ULIDs for public identifiers** — unguessable, sortable, index-friendly; signed URLs
   add tamper-proofing on top.

9. **MySQL for tests too** (not SQLite) — strict mode, unique-constraint semantics, and
   decimal handling are exactly where engines disagree, and money math + the
   `(tenant_id, number)` constraint must be tested on the real engine.

10. **Events for side effects** — `InvoicePaid` decouples the webhook from receipts and
    metrics, keeping it fast and retry-safe.

## 5. Security Highlights

- Tenant isolation via global scopes + middleware-set context, covered by tests.
- Signed URLs (`signed` middleware) for public invoice pages and email verification.
- Stripe webhook signature verification; CSRF exemption scoped to that one route.
- Rate limiting: API token issuance (10/min/IP), general API throttle, verification
  email resend throttle.
- ULID public IDs prevent enumeration; auto-increment IDs never leave the app.
- Sanctum bearer tokens, revocable per-token; plain text shown exactly once.
- Authorization through Laravel Policies; validation through Form Requests.

## 6. Testing Strategy

- **Pest feature tests against real MySQL** (separate `invoiceflow_saas_testing` DB).
- Coverage includes: API CRUD for clients/invoices/payments, **tenant isolation**
  (cross-tenant requests must 404/403), token auth, invoice payment flow,
  `MarkInvoicePaid`, the overdue scanner, reminder idempotency, and the Stripe webhook.
- Factories for all models; static analysis with Larastan; formatting with Pint.

## 7. Likely Interview Questions & Suggested Answers

**Q: How do you guarantee tenant isolation?**
A: A `BelongsToTenant` trait applies a global Eloquent scope reading from a
container-scoped `CurrentTenant` object that middleware sets from the authenticated
user (session or Sanctum token). It also auto-stamps `tenant_id` on create. Because a
missed scope would be a data leak, the test suite explicitly asserts cross-tenant
requests fail.

**Q: Why not database-per-tenant?**
A: At freelancer scale it multiplies operational cost — N migrations, N backups,
connection juggling — for isolation we don't need yet. Every table carries `tenant_id`,
so exporting a tenant to its own database later is mechanical.

**Q: How do you avoid duplicate invoice numbers under concurrent requests?**
A: Number generation is centralized in one service running inside a database
transaction, and a unique `(tenant_id, number)` constraint at the DB level is the final
guarantee.

**Q: Why integers for money?**
A: Floats can't represent decimal currency exactly and errors compound across line
items. Everything is minor units (cents) with an explicit currency column.

**Q: What happens if Stripe retries a webhook?**
A: The handler is idempotent — payment recording checks existing state, and side
effects (receipt email, metrics) run in queued listeners off an `InvoicePaid` event, so
the webhook itself stays fast and safe to replay.

**Q: How do reminders avoid double-sending?**
A: A `reminders_sent` marker on the invoice tracks which tier (+3/+7/+14) has fired;
the daily command skips already-sent tiers, so re-runs are safe.

**Q: What would you do next / how does it scale?**
A: Horizontal scaling is straightforward (stateless app + queue workers). Next steps:
per-line tax when needed, more payment providers behind the existing `PaymentProvider`
enum, team invitations for the Member role, read replicas if dashboards get heavy, and
the documented per-tenant DB migration path if an enterprise customer needs hard
isolation.
